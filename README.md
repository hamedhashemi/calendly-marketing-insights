# Calendly Marketing Insights — End-to-End AWS Data Engineering Pipeline

[![CI](https://github.com/hamedhashemi/calendly-marketing-insights/actions/workflows/ci.yml/badge.svg)](https://github.com/hamedhashemi/calendly-marketing-insights/actions/workflows/ci.yml)

[![CD](https://github.com/hamedhashemi/calendly-marketing-insights/actions/workflows/deploy.yml/badge.svg)](https://github.com/hamedhashemi/calendly-marketing-insights/actions/workflows/deploy.yml)

An end-to-end AWS data engineering project that ingests Calendly booking events and marketing spend data, transforms them through a Delta Lake medallion architecture, calculates marketing and operational metrics, and exposes analytics through Amazon Athena and Streamlit.

---

## Project Objective

The objective of this project is to build a production-oriented data engineering pipeline that helps the organization understand the relationship between marketing activity, Calendly bookings, and employee meeting workload.

The solution supports analysis of:

- Daily calls booked by marketing source
- Cost Per Booking (CPB) by channel
- Booking trends over time
- Marketing channel attribution
- Booking activity by hour and day of week
- Weekly employee meeting workload

The pipeline combines real-time Calendly webhook events with daily marketing spend data and converts them into analytics-ready Gold datasets.

---

## Business Problem

Marketing and scheduling data originate from different systems and arrive at different frequencies.

Calendly provides booking activity through webhooks, while marketing spend data is published separately as daily JSON files.

Without a centralized data pipeline, the organization cannot reliably answer questions such as:

- How many calls are generated by each marketing source?
- How much does each booked call cost?
- Which channels generate bookings efficiently?
- When are leads most likely to create bookings?
- How does booking volume change over time?
- How many meetings are employees handling each week?

This project solves that problem by integrating the sources into a common AWS-based analytics platform.

## Why These Technologies Were Used

### Amazon API Gateway

Calendly delivers booking activity through HTTP webhooks.

Amazon API Gateway provides a managed public endpoint that can receive webhook requests and forward them to Lambda without requiring a continuously running application server.

This makes it appropriate for event-driven ingestion.

### AWS Lambda

Lambda is used for two lightweight ingestion workloads:

1. Receiving Calendly webhook events
2. Retrieving daily marketing spend files

The workloads are event-driven and relatively small, so maintaining dedicated servers or clusters would introduce unnecessary infrastructure and operational overhead.

### Amazon S3

Amazon S3 serves as the central data lake.

It provides:

- Durable object storage
- Low operational overhead
- Scalability
- Integration with AWS Glue and Athena
- Separation between raw and transformed datasets

The project stores data in Landing, Bronze, Silver, and Gold layers.

### Delta Lake

Delta Lake is used on top of Amazon S3 to add transactional table behavior to object storage.

Important capabilities used by the project include:

- ACID transactions
- Delta transaction logs
- MERGE operations
- Schema enforcement
- Repeatable processing
- Transaction history
- Safer idempotent updates

Delta Lake is particularly valuable in the Silver layer, where records may need to be inserted or updated based on stable business keys.

### AWS Glue and PySpark

AWS Glue provides serverless Spark processing without requiring a persistent Spark cluster.

PySpark is used for:

- Reading Delta tables
- Flattening nested Calendly JSON
- Parsing timestamps
- Data quality validation
- Deduplication
- Business rule transformations
- Aggregation
- Joining booking and spend data
- Delta MERGE operations
- Gold dataset generation

### AWS Glue Data Catalog

The Glue Data Catalog provides metadata definitions for analytics tables stored in S3.

This enables Athena to query Delta datasets without the dashboard needing to understand the underlying S3 file structure.

### Amazon Athena

Athena provides a serverless SQL query layer over curated Gold data.

A dedicated warehouse such as Redshift was not required for the current project scale.

Athena allows the Streamlit application to query analytics-ready tables without maintaining database infrastructure.

### AWS Step Functions

The data pipeline contains several dependent Lambda and Glue operations.

Step Functions provides:

- Explicit workflow orchestration
- Parallel processing
- Retry behavior
- Execution history
- Failure visibility
- Controlled dependencies between jobs

The Calendly and Marketing Spend Silver pipelines can run in parallel before Gold datasets are generated.

### Amazon EventBridge Scheduler

Marketing spend data is published daily.

EventBridge Scheduler automatically starts the Step Functions workflow every day at:

```text
07:15 AM
America/New_York
```

The schedule intentionally provides a buffer after the expected marketing spend publication time.

Using `America/New_York` also allows the scheduler to handle daylight-saving time correctly.

### Amazon EventBridge and SNS

Failed Step Functions executions generate AWS service events.

An EventBridge Rule monitors execution statuses including:

```text
FAILED
TIMED_OUT
ABORTED
```

Matching events are sent to Amazon SNS.

SNS then delivers an email notification so pipeline failures do not remain unnoticed.

### Streamlit

Streamlit provides the project visualization layer.

The dashboard reads curated Gold datasets through Athena rather than performing core transformation logic inside the visualization application.

This keeps business logic in the data engineering layer and presentation logic in the dashboard layer.

### GitHub Actions

GitHub Actions provides automated Continuous Integration and Continuous Deployment.

CI validates code before deployment.

CD deploys only code that successfully passes CI.

### GitHub OIDC and AWS STS

GitHub Actions does not use long-lived AWS access keys.

Instead:

```text
GitHub Actions
      |
      v
GitHub OIDC Token
      |
      v
AWS STS
      |
      v
Temporary AWS Credentials
```

A repository-scoped IAM role allows GitHub Actions to deploy only the required Glue scripts and Lambda code.

## Data Sources

Calendly sends organization-level webhook events to Amazon API Gateway.

The current pipeline primarily processes:

```text

```

Webhook payloads contain fields related to:

- Invitee
- Scheduled event
- Event type
- Booking timestamp
- Meeting start and end time
- Tracking / UTM attributes
- Employee memberships
- Invitee count
- Rescheduling relationships

Raw webhook payloads are preserved in the Landing layer.

### Marketing Spend Data

Marketing spend data is provided through a public S3 source.

The source publishes a file index and daily JSON files.

Each marketing spend record contains:

```text
date
channel
spend
```

The supported spend channels are:

```text
facebook_paid_ads
youtube_paid_ads
tiktok_paid_ads
```

Spend values are interpreted as USD.

## Data Lake Architecture

The project implements a medallion architecture:

```text
Landing -> Bronze -> Silver -> Gold
```

Each layer has a distinct responsibility.

---

## Landing Layer

The Landing layer preserves source data with minimal transformation.

Its purpose is to support:

- Source preservation
- Auditability
- Replay
- Troubleshooting
- Recovery
- Reprocessing

### Calendly Landing

Location:

```text
s3://dea-calendly-marketing-hh/landing/calendly/
```

Calendly webhook events are stored using partition-style paths containing event type and date information.

Raw JSON is preserved.

### Marketing Spend Landing

Location:

```text
s3://dea-calendly-marketing-hh/landing/marketing_spend/
```

Marketing spend files are retrieved from the provided public source.

Each content version is identified using SHA-256.

Example structure:

```text
landing/marketing_spend/
    source_file=spend_data_YYYY-MM-DD.json/
        sha256=<content_hash>.json
```

If the same file is retrieved again with identical content, it is skipped.

If the source file changes, the new content version is retained.

## Bronze Layer

Bronze preserves source-level information in Delta tables.

### Calendly Bronze

Location:

```text
s3://dea-calendly-marketing-hh/bronze/calendly/webhook_events/
```

The Calendly Bronze table stores one record per Landing source file.

Important fields include:

- `source_path`
- `source_etag`
- `source_size_bytes`
- `source_modified_at`
- `webhook_event_type`
- `raw_json`
- `payload_hash`
- `json_valid`
- `ingested_at`

Previously ingested Landing objects are detected so repeat executions do not duplicate Bronze records.

### Marketing Spend Bronze

Location:

```text
s3://dea-calendly-marketing-hh/bronze/marketing_spend/
```

Marketing Spend Bronze preserves:

- Source file name
- Source publication date
- Source object path
- Content hash
- Raw JSON
- JSON validity
- Record count
- Retrieval metadata

Each source content version is preserved for lineage and replay.

## Silver Layer

Silver converts raw data into validated, structured business datasets.

### Calendly Booking Silver

Location:

```text
s3://dea-calendly-marketing-hh/silver/calendly/booking/
```

The Silver Calendly table uses one row per unique invitee booking.

Key transformations include:

- Filtering valid `invitee.created` events
- Flattening nested webhook JSON
- Extracting Calendly IDs from URIs
- Excluding known synthetic test events
- Validating required fields
- Parsing booking timestamps
- Parsing meeting timestamps
- Extracting tracking information
- Extracting employee membership information
- Identifying group events
- Classifying original bookings versus reschedules
- Marketing channel attribution
- Deduplication
- Delta MERGE processing

The Silver business key is:

```text
invitee_id
```

### Original Booking vs Reschedule

A new `invitee.created` event containing an `old_invitee` reference represents a rescheduled booking.

Therefore:

```text
old_invitee is NULL
        ->
Original Booking
```

and:

```text
old_invitee exists
        ->
Rescheduled Booking
```

Reschedules are retained for operational analysis but are not counted as new marketing acquisitions.

### Marketing Spend Silver

Location:

```text
s3://dea-calendly-marketing-hh/silver/marketing_spend/
```

Marketing Spend Silver uses the business key:

```text
spend_date + channel
```

Validation includes:

- Valid date
- Valid channel
- Valid spend value
- Valid source file
- Duplicate detection

When overlapping spend files contain the same business date and channel, the most recent valid source snapshot is selected.

The Silver table is updated using Delta MERGE.

## Marketing Attribution

Marketing attribution is intentionally conservative.

The pipeline does not classify Calendly events into marketing channels based only on names or assumptions.

Only project mappings that were explicitly confirmed are used.

The currently confirmed active Calendly mapping is:

```text
Data Engineer Academy Breakthrough Session FB D2C Var
```

Event Type ID:

```text
d5c9e359-c580-4c11-8bf5-531a3de5ae5c
```

Mapped channel:

```text
facebook_paid_ads
```

YouTube and TikTok marketing spend data is retained in the pipeline, but their currently active Calendly event mappings have not yet been confirmed.

Therefore the pipeline does not fabricate booking counts or CPB values for those channels.

UTM fields such as:

```text
utm_source
utm_campaign
```

are preserved where available, but Event Type mapping currently provides the primary attribution method because UTM fields are frequently unavailable in the source data.

## Gold Layer

Gold contains analytics-ready business datasets.

Three Gold datasets are currently used.

---

### Daily Marketing Performance

Location:

```text
s3://dea-calendly-marketing-hh/gold/daily_marketing_performance/
```

Grain:

```text
report_date + channel
```

The table combines marketing spend and attributed Calendly bookings.

Metrics include:

- Spend amount
- Currency
- All created bookings
- Original bookings
- Rescheduled bookings
- Mapping status
- Booking coverage status
- Spend availability
- CPB status
- Cost Per Booking

### Cost Per Booking

The primary business formula is:

```text
CPB = Total Spend / Original Bookings
```

Rescheduled bookings are not counted as new acquisitions.

CPB is calculated only when:

- Channel mapping is confirmed
- Booking data coverage is complete
- Spend data exists
- At least one original booking exists

Possible CPB statuses include:

```text
ready
mapping_pending
booking_data_incomplete
spend_missing
zero_original_bookings
```

For multi-day or aggregate reporting:

```text
Aggregate CPB =
SUM(Spend) / SUM(Original Bookings)
```

Daily CPB values should not be averaged directly.

---

### Booking Time Analysis

Location:

```text
s3://dea-calendly-marketing-hh/gold/booking_time_analysis/
```

The dataset supports analysis of:

- Booking volume by hour
- Booking volume by weekday
- Hour × weekday heatmap
- Booking trends by source
- Original versus rescheduled bookings

Calendly timestamps are stored in UTC but analytics are normalized to:

```text
America/New_York
```

This ensures daily and hourly metrics reflect the business reporting timezone.

The primary booking metric is based on original bookings.

---

### Employee Meeting Load

Location:

```text
s3://dea-calendly-marketing-hh/gold/employee_meeting_load/
```

This dataset supports employee workload analysis.

The correct meeting grain is:

```text
employee_id + event_id
```

rather than invitee count.

This is important because a group event may contain multiple invitees while still representing only one meeting for an employee.

Example:

```text
5 Invitees
     |
     v
Same Scheduled Event
     |
     v
Same Employee
     |
     v
1 Employee Meeting
```

The table supports:

- Weekly meeting count
- Total employee meetings
- Number of observed weeks
- Average meetings per week
- Employee workload trends

The requirement formula is:

```text
Average Meetings per Week =
Total Meetings / Number of Weeks
```

The current implementation measures scheduled meeting workload.

It does not prove that an employee actually attended or completed every scheduled meeting.

## Failure Handling

Production-level failure handling is implemented at multiple layers.

### Step Functions Retry

Lambda and Glue tasks are configured with retry behavior for execution failures.

### Data-Level Idempotency

Retrying the pipeline does not intentionally create duplicate business records.

The strategy differs by layer.

#### Marketing Spend Landing

```text
SHA-256 content version
```

Existing identical content is skipped.

#### Calendly Bronze

```text
source_path
```

Already ingested Landing objects are not inserted again.

#### Calendly Silver

```text
invitee_id
```

Delta MERGE inserts new bookings and updates changed records.

#### Marketing Spend Silver

```text
spend_date + channel
```

Delta MERGE maintains one current record per business key.

#### Gold

Gold datasets are deterministic transformations derived from validated Silver datasets.

This allows failed executions to be safely retried.

## Security

### Encryption at Rest

Data stored in Amazon S3 is protected using Amazon S3 server-side encryption.

### Encryption in Transit

AWS service communication and external API communication use HTTPS/TLS.

### IAM

Services use IAM roles rather than hard-coded AWS credentials.

Permissions are scoped according to service responsibilities.

### GitHub CI/CD Authentication

GitHub Actions uses OIDC federation with AWS.

The deployment process is:

```text
GitHub Actions
      |
      v
OIDC Identity Token
      |
      v
AWS STS
      |
      v
Temporary Credentials
      |
      v
github-calendly-deploy-role
```

No long-lived AWS access keys are stored in GitHub Secrets.

The deployment role is restricted to the required S3 script objects and Lambda functions.

### Personally Identifiable Information

Raw Calendly webhook data can contain PII such as:

- Names
- Email addresses
- Phone numbers
- Meeting information

Raw Landing data remains private in S3 and is not committed to GitHub.

PII is minimized in Silver and Gold datasets.

Meeting credentials and sensitive raw payload details are not exposed through the dashboard.

### Webhook Signature Limitation

The current Calendly subscription was created without a webhook signing key.

As a result, the current implementation does not cryptographically verify webhook authenticity.

This limitation is explicitly documented instead of representing the inbound webhook as signed or authenticated when it is not.

Workflow:

After a successful CI run on `main`, CD:

1. Checks out the exact Git commit that passed CI
2. Requests a GitHub OIDC token
3. Assumes an AWS IAM role through AWS STS
4. Receives temporary AWS credentials
5. Deploys six Glue scripts to their existing S3 locations
6. Packages and updates both existing Lambda functions

AWS deployment role:

```text
github-calendly-deploy-role
```

The CD pipeline updates:

```text
6 AWS Glue scripts
2 AWS Lambda functions
```

CD does not execute Step Functions or Glue jobs.

Operational data processing remains controlled independently through:

```text
EventBridge Scheduler -> Step Functions
```

This separation prevents normal source-code deployment from unintentionally triggering production ETL processing.

The complete CI and CD workflows have been successfully executed.

## Important Business Rules

### Original Bookings

Marketing acquisition metrics count only original bookings.

```text
old_invitee is NULL
        ->
New Acquisition
```

Rescheduled bookings remain available for operational reporting but are not treated as new leads.

### Group Events

Employee meeting load is based on:

```text
employee_id + event_id
```

not invitee count.

### CPB

CPB uses:

```text
Total Spend / Original Bookings
```

For multiple dates:

```text
SUM(Spend) / SUM(Original Bookings)
```

### Attribution

Only confirmed Calendly-to-marketing mappings are used.

Unknown mappings are represented as unknown or pending rather than being converted to zero-booking channels.

## Known Limitations

The project intentionally documents limitations that cannot be solved reliably from the currently available source data.

### YouTube and TikTok Attribution

Marketing Spend includes:

```text
facebook_paid_ads
youtube_paid_ads
tiktok_paid_ads
```

However, only the current Facebook Calendly Event Type mapping has been confirmed.

Active YouTube and TikTok Calendly mappings remain pending.

Therefore CPB for those channels is not represented as fully attributable booking performance.

### UTM Coverage

Calendly UTM tracking fields are often null.

The pipeline preserves the fields when present but does not rely exclusively on UTM data for attribution.

### Employee Attendance

The pipeline measures scheduled meeting workload.

It does not contain independent evidence proving that every scheduled meeting actually occurred or that an employee attended it.

### Cancellations

The current primary Silver booking model focuses on `invitee.created`.

Full cancellation-state modeling can be added as a future enhancement.

### Webhook Authentication

The active Calendly webhook subscription does not include a signing key.

Therefore webhook authenticity is not cryptographically verified in the current implementation.

## Business Outcome

The completed pipeline converts raw scheduling and advertising data into a repeatable analytics platform.

It provides a foundation for answering business questions related to:

- Marketing acquisition cost
- Booking volume
- Channel attribution
- Booking behavior
- Campaign performance
- Calendar optimization
- Employee meeting workload

The architecture deliberately separates:

```text
Ingestion
Transformation
Storage
Orchestration
Analytics
Visualization
Deployment
```

This separation allows each component to evolve independently while preserving source lineage, data quality, and operational reliability.

This project demonstrates an end-to-end AWS data engineering workflow that integrates real-time webhook ingestion and scheduled batch ingestion into a Delta Lake architecture.

The solution implements:

```text

      |
      v

      v
```

Operational execution is managed through:

```text

        |

        v

```

Code deployment is managed independently through:

```text
GitHub
   |
   v

   |
   v

   |

   |
```

The result is a scalable, auditable, idempotent, and production-oriented analytics pipeline that transforms Calendly and marketing spend data into actionable business insights.
